## Headline

Against the defragmenter Windows 95 actually shipped, on the same volume, the same drive and a held-out workload:

* **cold boot 33.8% less disk time** (3783 ms -> 2506 ms)
* **a modelled working day 24.5% less disk time** (32.2 s -> 24.3 s)

For scale: the shipped defragmenter itself only bought 19.0% on boot over not defragmenting at all, and defrag95 buys 46.3%.

Mean ± population standard deviation over 5 independent evaluation workloads, none of which the layout planner was allowed to see.

The two middle columns are the ones to read if the question is whether defragmenting was worth doing at all. Over a whole working day the shipped defragmenter is 2.0% better than leaving the volume alone, because its boot and launch wins are largely cancelled by the paging storm, which it makes **20.7% worse**: it packs every file against the front of the volume but cannot move the in-use swap file, so it drags application code away from the 197-piece swap file it pages against. Run from DOS, where the swap file can be moved, that regression disappears.

## Where the boot time goes

| Layout | Seek | Rotational latency | Transfer | Per-request overhead | Total |
|---|---:|---:|---:|---:|---:|
| No defrag (aged volume) | 1381 ms | 1077 ms | 2128 ms | 83 ms | 4668 ms |
| Win95 Defrag - files only | 1378 ms | 1063 ms | 2111 ms | 82 ms | 4635 ms |
| Win95 Defrag - full (as shipped) | 671 ms | 1063 ms | 1966 ms | 82 ms | 3783 ms |
| Win95 Defrag - full, DOS mode | 677 ms | 1063 ms | 1965 ms | 82 ms | 3788 ms |
| defrag95 | 109 ms | 347 ms | 1968 ms | 82 ms | 2506 ms |

The shipped defragmenter attacks fragmentation, which is mostly a *seek* problem. Ordering by observed access turns unrelated reads into near-sequential ones, which additionally collapses rotational latency, because the drive's own read-ahead buffer has already fetched the next file by the time it is asked for.

## Does the layout survive use?

Each layout is then put through another 90 days of the same simulated use -- same seed, same operations, so every layout faces identical churn -- and then each defragmenter is run again.

| Layout | Boot, fresh | Boot, +90d | Decay | Extents/file, +90d | Re-run moves | Boot after re-run |
|---|---:|---:|---:|---:|---:|---:|
| No defrag (aged volume) | 4668 ms | 4824 ms | +3.3% | 1.43 | 0 MB | 4824 ms |
| Win95 Defrag - files only | 4635 ms | 4857 ms | +4.8% | 1.18 | 92 MB | 4784 ms |
| Win95 Defrag - full (as shipped) | 3783 ms | 4008 ms | +6.0% | 1.09 | 1077 MB | 3827 ms |
| Win95 Defrag - full, DOS mode | 3788 ms | 3982 ms | +5.1% | 1.08 | 1128 MB | 3831 ms |
| defrag95 | 2506 ms | 3209 ms | +28.1% | 1.11 | 204 MB | 2708 ms |

defrag95's layout decays faster in relative terms, and that is the honest shape of the result: it starts from a much better place, and the same churn costs it more. In absolute terms it is still 799 ms ahead of a freshly defragmented Win95 volume after 90 days without maintenance (3209 ms vs 4008 ms), and re-running it costs 204 MB of movement against 1077 MB for a full Win95 pass.

The re-run is a maintenance pass: both defragmenters leave a file alone if it is still contiguous and still within 16 MB of where the pass would put it, and move only what has drifted. The design's answer to decay is that pass running nightly on idle, not a cleverer one-shot -- which is what Windows 98 eventually shipped as a scheduled task.

## Cost of running the defragmenter

| Layout | Clusters relocated | Data moved | Lower-bound run time |
|---|---:|---:|---:|
| Win95 Defrag - files only | 4629 | 152 MB | 1.8 min |
| Win95 Defrag - full (as shipped) | 37723 | 1236 MB | 12.4 min |
| Win95 Defrag - full, DOS mode | 39004 | 1278 MB | 12.8 min |
| defrag95 | 39049 | 1280 MB | 13.0 min |

defrag95 moves slightly more data than a full Win95 pass on its first run, because it is not only removing fragmentation but relocating by use. That is a one-off overnight cost; the maintenance passes after it are far cheaper (see above).

Two of those rows deserve a caveat rather than a claim. **Volume fill** barely moves the boot number because both defragmenters put the boot set at the front of the volume whatever else is on it. It does change the volume underneath -- 68% versus 93% full after ageing, 1.31 versus 1.43 extents per file -- it just does not change this measurement. **Cache size** barely moves anything because a cold boot reads mostly distinct blocks: the measured VCACHE hit rate during boot is 0.7%. That is a consequence of measuring cold starts, which is the conservative choice here, not a claim that VCACHE did not matter in 1996.

Boot gain across every configuration tested: 14.2% to 42.2% (median 33.8%).
